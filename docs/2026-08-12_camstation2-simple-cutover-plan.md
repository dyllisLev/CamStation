# CamStation 1.0 → Docker 2.0 최소중단 전환 계획

이 문서가 실제 전환의 실행 기준이다. 카메라 연결정보와 현재 8타일 레이아웃을 반영해 로컬에서
검증한 2.0 DB를 운영에서도 그대로 사용한다. 전환 중 새 DB 생성이나 재-import는 하지 않는다.

## 고정 조건

- 로컬 개발 서버는 운영 서버와 출발 IP가 달라 운영 1.0과 동시에 카메라 8대를 수신할 수 있다.
- 운영 서버에서는 1.0과 2.0이 같은 출발 IP를 사용하므로 동시에 카메라를 수신하지 않는다.
- 로컬 Docker는 녹화를 끄고, 운영 Docker만 30분 단위 녹화를 사용한다.
- 현재 1.0의 카메라 연결정보 `9대/활성 8대/소방서2 비활성`과 8타일 레이아웃만 승계한다.
- 현재 1.0 서버와 Viewer는 2.0 최종 수락 전까지 삭제하지 않는다. 실패 시 즉시 다시 사용한다.
- HTTP와 WebRTC는 로컬·운영 모두 `10` 대역과 `192` 대역에 공개해야 한다.
- 실제 전환 순서는 아래 1~5단계에서 바꾸지 않는다.

## 고정 주소와 포트

| 대상 | HTTP | WebRTC candidate 및 공개 포트 |
|---|---|---|
| 로컬 개발 서버 관리망 | `http://10.0.0.16:18080` | `10.0.0.16:18555` TCP+UDP |
| 로컬 개발 서버 모니터링망 | `http://192.168.0.154:18080` | `192.168.0.154:18555` TCP+UDP |
| 운영 서버 관리망 | `http://10.0.0.26:18080` | `10.0.0.26:18555` TCP+UDP |
| 운영 서버 모니터링망 | `http://192.168.0.160:18080` | `192.168.0.160:18555` TCP+UDP |

go2rtc API와 RTSP 포트는 외부에 공개하지 않는다. 모니터링 PC는 `192` 대역을 사용하고, 관리용
브라우저는 `10` 대역을 우선 사용한다. 두 대역 중 하나라도 HTTP 또는 WebRTC가 빠지면 전환하지 않는다.

## 전환 전에 끝낼 준비

다음 항목은 영상 중단 전에 모두 끝낸다.

1. 현재 1.0 전체화면 캡처를 기준 화면으로 보관한다.
2. 로컬 검증 DB가 카메라 `9/8/1`, 레이아웃 `1/8`, SQLite quick-check `ok`인지 확인한다.
3. 로컬 Docker는 녹화 비활성, 운영 Docker는 녹화 활성·30분 세그먼트·700GB 정책인지 확인한다.
4. 로컬·운영 Compose가 위 표의 양쪽 HTTP와 WebRTC TCP+UDP를 모두 렌더링하는지 확인한다.
5. 운영 `camstation2` 컨테이너는 검증된 이미지와 DB로 `Created` 상태에 두고 시작하지 않는다.
6. 1.0의 정확한 stop/start 명령과 2.0의 start/stop 명령을 바로 실행할 수 있게 준비한다.
7. nginx의 기존 1.0 설정과 2.0 설정, 검증 및 원자적 전환·복구 명령을 준비한다.
8. 모니터링 PC에는 Viewer 2.0을 실행할 준비를 해 두되, 1단계의 로컬 브라우저 검증이 끝날 때까지
   기존 Viewer 1.0 화면을 유지한다.

## 1. 로컬 개발 Docker에서 카메라 8대 확인

이 단계는 운영 영상 중단 없이 수행한다.

1. 로컬 Compose 렌더링을 확인한다.
2. `camstation2-local-full-test`를 시작한다.
3. 다음 두 주소가 모두 응답하는지 확인한다.
   - `http://10.0.0.16:18080`
   - `http://192.168.0.154:18080`
4. 두 주소에 대해 `18555/TCP+UDP` listener와 광고 candidate가 일치하는지 확인한다.
5. 로컬 브라우저에서 `/live`를 열어 현재 1.0과 같은 8타일 레이아웃과 실제 움직이는 영상 8개를
   확인한다. 단순 상태값이나 썸네일만으로 합격시키지 않는다.
6. recorder worker와 새 녹화 파일이 0인지 확인한다.

합격 기준은 카메라 8대 실제 재생, 레이아웃 일치, 녹화 0, 양쪽 대역 공개다.

## 2. 모니터링 PC를 Viewer 2.0 + 로컬 Docker로 전환

이 단계부터 모니터링 PC는 Viewer 1.0이 아니라 Viewer 2.0으로 실제 화면 서비스를 계속한다.
모니터링 PC 브라우저는 사용하지 않는다.

1. 기존 Viewer 1.0을 정상 종료한다. 이 시각을 첫 화면 전환 시작 `T0`로 기록한다.
2. Viewer 2.0 서버 주소를 `http://192.168.0.154:18080`으로 설정한다.
3. Viewer 2.0을 실행 또는 재시작한다.
4. 현재 1.0과 같은 8타일 레이아웃에서 카메라 8대의 시간이 실제 진행하는지 확인한다.
5. WebRTC가 `192.168.0.154:18555`로 연결됐고 재시도·MSE fallback·대체 스트림이 없는지 로그로
   확인한다.
6. Viewer 2.0을 전체화면으로 전환하고 캡처한다. 이 시각을 `T1`로 기록한다.
7. Viewer 2.0 자동시작을 활성화한다. 이후 운영 전환 중에도 모니터링 PC는 로컬 Docker 2.0 영상을
   계속 표시한다.

이 단계가 실패하면 Viewer 1.0을 다시 실행하고 운영 전환을 시작하지 않는다. 성공하면 로컬 Docker를
끄지 않고 5단계가 끝날 때까지 유지한다.

## 3. 운영 1.0 종료 후 Docker 2.0 시작

이 단계에서는 모니터링 PC가 로컬 Docker 2.0 영상을 계속 표시하므로 운영 서버의 1.0 종료·2.0
시작 시간이 모니터링 화면 중단으로 이어지지 않는다.

1. 전환 lock을 획득하고 운영 1.0의 현재 상태를 마지막으로 짧게 확인한다.
2. 영상과 무관한 backup 서비스를 먼저 정상 종료한다.
3. 운영 1.0 backend와 go2rtc를 정확한 unit으로 정상 종료한다.
4. 1.0 카메라 receiver와 기존 카메라 수신 포트가 해제됐음을 확인한다.
5. 준비된 `camstation2` 컨테이너를 시작한다. 이 시점에 재생성·DB 복사·재-import를 하지 않는다.
6. health, 카메라 `9/8/1`, active live 8개, recorder worker 8개를 짧게 확인한다.

운영 1.0과 Docker 2.0의 카메라 수신은 겹치지 않는다.

## 4. 운영 서버를 브라우저로 확인하고 도메인 전환

1. 관리 브라우저에서 `http://10.0.0.26:18080/live`를 열어 8개 영상이 실제로 움직이는지 확인한다.
2. `http://192.168.0.160:18080`도 응답하는지 확인한다.
3. `10.0.0.26:18555`와 `192.168.0.160:18555`의 TCP+UDP listener 및 두 candidate를 확인한다.
4. WebRTC 첫 시도 성공 여부와 재시도·fallback 수를 구조화 로그로 확인한다.
5. 위 조건이 모두 맞으면 nginx를 1.0에서 검증된 2.0 upstream으로 원자 전환하고 `nginx -t` 후 reload한다.
6. `cctv2.nuc.hmini.me`가 2.0 health와 `/live`를 반환하는지 확인한다.

직접 주소에서 8대가 90초 안에 나오지 않으면 nginx와 모니터링 PC를 건드리지 않고 운영 서버를
즉시 1.0으로 복구한다. 모니터링 PC는 그동안 로컬 Docker 2.0 영상을 계속 표시한다.

## 5. 모니터링 PC의 Viewer 2.0을 운영 서버로 변경

Viewer 1.0은 이미 2단계에서 종료됐고, 현재 Viewer 2.0은 로컬 Docker를 표시하고 있다.

1. Viewer 2.0의 서버 주소 변경 직전을 `T2`로 기록한다.
2. Viewer 2.0 서버 주소를 `https://cctv2.nuc.hmini.me`로 변경한다.
3. `autoStart=true`를 유지한 채 Viewer 2.0을 재시작한다.
4. 운영 서버의 같은 8타일 레이아웃에서 카메라 8대의 시간이 실제 진행하는지 확인한다.
5. WebRTC가 운영 모니터링망 `192.168.0.160:18555`로 연결됐는지 확인한다.
6. Viewer 2.0을 전체화면으로 전환하고 전체 데스크톱 캡처를 보관한다.
7. 화면 복구 시각을 `T3`로 기록한다. `T3 - T2`가 운영 주소 변경으로 인한 두 번째 화면 중단 시간이다.
8. 운영 Viewer 2.0이 합격한 뒤 로컬 Docker를 정상 종료한다.

첫 번째 중단은 Viewer 1.0에서 로컬 Viewer 2.0으로 바꾸는 `T1 - T0`, 두 번째 중단은 로컬 주소에서
운영 주소로 Viewer 2.0을 재시작하는 `T3 - T2`다. 운영 서버 1.0→2.0 전환 시간에는 로컬 2.0 화면이
계속 표시된다. 각 Viewer 전환의 목표는 30초 이내이며 90초는 즉시 복구 상한이다.

## 화면 복구 후 녹화 확인

화면이 복구된 뒤 수행하며 영상 중단 시간에 포함하지 않는다.

1. recorder worker 8개가 실행 중인지 확인한다.
2. 활성 카메라 8개의 열린 녹화 파일 크기가 증가하는지 확인한다.
3. 30분 세그먼트가 종료·확정되고 다음 파일로 rollover되는지 확인한다.
4. 카메라 8대, 도메인, Viewer 전체화면, 녹화 결과를 최종 기록한다.

## 즉시 복구

다음 중 하나면 2.0을 현장에서 수정하지 않고 복구한다.

- 90초 안에 운영 직접 브라우저에서 8대 실제 영상이 나오지 않는다.
- 카메라가 8대 미만이거나 정지·반복 재연결 상태다.
- 양쪽 대역의 HTTP/WebRTC 공개가 계획과 다르다.
- 도메인 전환 또는 Viewer 2.0의 8타일 전체화면이 실패한다.

복구 순서:

1. 2단계의 로컬 Viewer 2.0 전환이 실패하면 Viewer 2.0을 종료하고 Viewer 1.0을 다시 실행한다.
2. 운영 서버 전환이 실패하면 Docker 2.0을 정상 종료하고 보존한 운영 1.0
   backend/go2rtc/backup을 시작한다. 모니터링 PC는 로컬 Viewer 2.0을 계속 표시한다.
3. nginx를 이미 변경했다면 기존 1.0 설정으로 되돌리고 검증 후 reload한다.
4. 5단계의 운영 주소 변경이 실패하면 Viewer 2.0 주소를 로컬
   `http://192.168.0.154:18080`으로 되돌려 재시작한다. 로컬 Docker는 이 단계가 합격할 때까지
   종료하지 않는다.
5. 운영 1.0을 복구할 경우 Viewer 1.0까지 원래 상태로 되돌릴지, 로컬 Viewer 2.0 서비스를 계속
   유지할지는 복구 시점의 운영 지시에 따른다.
6. 선택한 복구 화면에서 8타일 라이브가 다시 움직이는지 확인하고 전체 화면을 캡처한다.

1.0 프로그램·DB·설정은 수락 완료 전까지 보존하므로 복구 과정에서 DB 복원이나 재변환은 하지 않는다.
