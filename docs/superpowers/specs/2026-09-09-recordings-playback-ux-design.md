## 요구와 설계 경계

목록이 재생 화면보다 크고 페이지 스크롤 시 영상이 사라지는 문제를 해결한다. 기성 NVR의 재생 UX를 조사하고 대안 3개를 비교한다. 사용자 수정에 따라 현재 배포 웹 화면과 모니터링 PC의 실제 Viewer를 먼저 확인하며, 각 화면의 기존 프레임 안에서 본문만 재설계한다.

## 공통 재생 작업 영역

1. 위쪽 한 줄: 카메라 이름 선택, 날짜, 정확한 KST 시각 입력, 배치·목록 토글. 날짜 선택 달력은 팝오버로 열어 평소 공간을 차지하지 않는다.
2. 중앙: 가장 큰 영역을 영상에 할당. 기본 원본 비율 유지, 레터박스 허용. 영상 확대는 별도 조작이며 영상 왜곡 금지.
3. 영상 아래: 이전/다음 구간, ±10초, 재생/일시정지, 배속, 음량, 전체화면. 현재 시각은 파일 내 경과시간과 구분한다.
4. 맨 아래: 녹화 있음/없음과 현재 재생 위치를 보여 주는 시간축. 시간축 확대·축소와 이동, 하루 개요 표시. 파일 경계는 사용자에게 매번 선택을 요구하지 않는 연속 시간 탐색으로 연결한다.
5. 목록을 열면 해당 패널만 독립 스크롤한다. 목록·필터 변경은 현재 영상을 임의로 닫거나 재생 시각을 초기화하지 않는다. 구간 선택 시 동일 플레이어에서 재생한다.

문서 전체를 길게 늘리는 방식 대신 실제 헤더 높이를 제외한 가용 높이에 작업 영역을 맞춘다. 고정 64px 가정은 사용하지 않는다. 기존 main의 최소 높이·padding 때문에 생기는 추가 스크롤도 녹화 경로 범위에서 조정해야 한다. 다른 콘솔 페이지의 셸은 바꾸지 않는다.

## 비교할 세 가지 배치

- A 집중형: 목록은 기본 닫힘. 비교용 시안이며, 최신 선택은 B 탐색형이다.
- B 탐색형: 사용자가 선택한 녹화 화면 기본값. 큰 단일 영상 + 우측 약 320px 구간 목록. 목록은 시간/길이 중심이며 영상은 제자리에 유지한다. 썸네일 생성은 별도 미확정 항목이다.
- C 동기형: 비교 목업이다. 최신 선택에서는 별도 녹화 화면 배치로 구현하지 않고 기존 라이브 그리드와 타임라인에 통합한다. 대상 수는 목업의 4개 제한 대신 현재 라이브 배치에 표시되는 카메라를 따른다.

녹화 페이지는 B 탐색형 단일 재생, 라이브 페이지는 기존 그리드에서 라이브/다중 녹화 재생을 전환한다. 절대시각 기반 탐색과 녹화 재생 계층은 공유한다.


## 최신 사용자 합의: 화면 구성과 모드 전환

2026-09-09 추가 요구를 기존 비교 시안보다 우선 적용한다.

### 확정 요구

추가 정정: 사용자가 말한 큰 화면은 기존 `집중 보기` 기능이다. 아래 확대 요구는 이 기능에 재생 상태를 연동하는 뜻이며, 영상 더블클릭 줌 초기화 등 기존 제스처 변경은 포함하지 않는다.

- 녹화 화면은 2번(B 탐색형): 큰 단일 영상, 우측 구간 목록, 하단 시간축. 목록만 독립 스크롤하며 영상과 필수 조작부는 화면에 유지한다. 카메라·날짜·KST 절대시각으로 탐색한다.
- 다중 동기 재생은 기존 라이브 화면에 통합한다. 기존 타임라인에서 특정 절대시각을 누르면 현재 배치의 모든 카메라가 해당 시각의 녹화 재생으로 전환한다. 재생 모드에서 다시 누르면 공통 재생 위치를 변경한다.
- 기존 카메라 집중 보기 확대는 현재 라이브/재생 모드를 따른다. 재생 모드에서는 선택 카메라를 같은 재생 흐름으로 확대하며 현재 시각, 재생/일시정지, 배속을 유지한다. 그리드로 복귀해도 현재 공통 시각과 상태를 유지한다.
- 타임라인에 LIVE 버튼을 추가한다. 라이브 모드에서 켜짐, 재생 모드에서 꺼짐으로 표시하되 재생 중에도 클릭 가능하다. 클릭하면 전체 작업 영역을 라이브로 복귀시킨다. 확대 중에도 동일하게 동작한다.
- 모드와 현재 시각은 그리드·확대 보기 모두 명확히 표시한다. 녹화 재생 중 현재 벽시계를 재생 위치로 표시하지 않는다.
- 진행 중인 녹화도 완성된 fMP4 조각부터 재생한다. 30분 파일 완료를 기다리지 않으며 절대시각과 미디어 시각의 대응을 저장한다. 과거 일반 MP4도 재생을 유지한다.

### 구현 기본값과 남은 측정 항목

다음은 확정 요구를 일관되게 구현하기 위한 기본값이다. 별도 기능 확장으로 취급하지 않는다.

- '모든 영상'은 현재 라이브 배치에 포함된 카메라다. 확대는 그중 한 카메라를 보여 주는 상태이며 공통 재생 시계는 유지한다.
- 재생/일시정지와 배속은 공통으로 적용한다. 확대 중 시간 탐색도 전체 배치의 공통 시각을 바꾼다. 숨겨진 타일의 디코딩 유지 여부는 자원 관리 구현 사항이다.
- 선택 시각에 녹화가 없는 카메라는 '녹화 없음'을 표시한다. 로딩·실패와 구분하며 해당 카메라만 라이브로 대체하거나 다른 카메라의 시각을 이동시키지 않는다. 녹화가 다시 있는 시각이 되면 공통 시각에 맞춰 참여한다.
- 최신 재생 가능 끝에 도달하면 새 녹화를 기다리며 재생 모드를 유지한다. 자동 라이브 전환은 하지 않고 LIVE 버튼으로 명시적으로 복귀한다.
- 라이브 배치와 저장된 줌/팬은 보존한다. 모드 전환이나 확대를 이유로 초기화하지 않는다.
- 절대시각 기준이 서버 수신 시각인지 카메라 촬영 시각인지 구분하고 시간 매핑 정확도를 검증한다. 로컬과 테스트 PC의 실제 최대 2대 카메라로 같은 시각 탐색·최신 녹화 재생·라이브 복귀 동작을 확인한다. 부하 검사나 별도 성능 허용 기준은 두지 않는다. 과거 파일의 부족한 시각 정보를 정밀하게 복구했다고 주장하지 않는다.
- 썸네일·구간 내보내기·분석 이벤트는 이번 선택만으로 필수 기능에 추가하지 않는다. 기존 권한과 다운로드·관리 기능은 유지한다.

### Synology 공식 자료 추가 확인

사용자 요청에 따라 2026-09-09 온라인 공식 자료를 확인했다. 이전 구버전 Timeline 안내보다 Surveillance Station 9의 Monitor Center를 화면 동작 참고 기준으로 삼는다.

- [Live View와 Timeline 통합 안내](https://kb.synology.com/en-global/Surveillance/tutorial/LiveView_Timeline_merged_into_MonitorCenter_in_SS9): 9.0에서 두 기능을 Monitor Center로 합쳤으며 한 레이아웃에서 라이브와 녹화를 볼 수 있다. 하단 시간축에 탐색과 재생 조작을 배치한다.
- [Monitor Center 조작 설명](https://kb.synology.com/en-eu/SurveillanceStation/help/SurveillanceStation/monitor_center_display_controls): Sync는 전체 채널 동시 재생/개별 재생을 선택하며, LIVE는 라이브 보기로 복귀한다. 달력의 날짜·시간 이동, 시간축 확대·축소, 녹화 유형 구분, 재생/일시정지·10초 이동·배속 기능을 설명한다.
- [다중 카메라 Timeline 안내](https://kb.synology.com/en-me/SurveillanceStation/help/SurveillanceStation/Tutorial/watch_timeline): Sync 모드에서 커서를 움직이면 모든 영상이 특정 시점으로 함께 이동한다고 명시한다. 이 페이지는 분리된 Timeline 앱 기준의 과거 구조이므로 현재 화면 배치의 근거로 사용하지 않는다.
- [현행 기능 사양](https://www.synology.com/en-us/dsm/7.4/software_spec/surveillance_station): Monitor Center의 녹화 타임라인과 Recording Player를 별도로 설명한다. 이는 관제 중 시간 탐색과 녹화 자료 탐색을 함께 제공하는 구조의 참고 근거다. B 시안의 정확한 화면 배치가 Synology와 동일하다는 의미는 아니다.

CamStation 적용: 기존 라이브 화면의 하단 시간축과 LIVE 복귀를 연결하고, 이번 요구에서는 공통 동기 재생을 기본으로 한다. Synology의 개별 비동기 모드, 이벤트 분석, 북마크, 역재생까지 자동으로 범위를 확대하지 않는다. 별도 녹화 화면은 사용자가 선택한 B 탐색형을 유지한다.

확인 한계: 검색한 공식 문서만으로 더블클릭 전후 재생 상태 보존의 세부 계약, LIVE 버튼의 정확한 점등 규칙, 진행 중 녹화의 내부 fMP4 사용 여부는 확인하지 못했다. 확대 시 상태 유지와 LIVE 점등은 사용자 요구에 따른 CamStation 계약이며, fMP4는 별도 기술 실험에 근거한 구현 방향이다.

### 완료 확인 시나리오

1. B 녹화 화면에서 긴 목록을 스크롤해도 영상과 조작부가 유지되고, 구간/절대시각 선택이 실제 재생 위치와 일치한다.
2. 라이브 그리드 타임라인 클릭으로 표시 카메라 전체가 공통 절대시각 재생으로 전환하고 LIVE 표시가 꺼진다.
3. 재생 중 기존 집중 보기 확대/복귀에서 시각·배속·일시정지가 유지되며 라이브로 잘못 전환되지 않는다. 라이브 모드 확대도 기존 동작을 유지한다.
4. 그리드와 확대 보기에서 LIVE 버튼으로 실제 라이브 스트림에 복귀하며 기존 배치·줌/팬이 보존된다.
5. 일부 카메라의 공백·로딩·실패가 다른 카메라를 다른 시각으로 이동시키지 않는다. 파일 경계와 자정 경계에서도 시간 매핑이 유지된다.
6. 실제 녹화가 계속되는 동안 최근 완성 조각을 재생하고, 파일 마감·이동·재시작 후에도 과거 및 신규 녹화 재생을 확인한다.
7. 로컬 관리자 콘솔과 테스트 PC의 Windows Viewer에서 각각 화면·권한·모드 전환을 검증한다. 기존 녹화·백업·삭제 보호 검사를 통과한다.

## 추가 구현 의존성

파일 단위 목록·상세·재생·다운로드 외에 기존 `/api/timeline?cam=...&date=...`도 있다. 초기 설계에서 이 API와 현재 라이브 시간축의 미완성 상태를 충분히 조사하지 못했다. 아래 추가 타당성 확인을 기준으로 기존 API를 보완·재사용한다. 다음은 목업의 제안 기능이며 기존 구현 완료로 간주하지 않는다.

- 기존 날짜별 `/api/timeline`은 DB를 조회하며 콘솔 목록의 limit 200 제한을 사용하지 않는다. 다만 시작 시각이 당일인 파일만 찾으므로 날짜를 가로지르는 파일이 누락될 수 있다. 범위와 겹치는 구간 조회로 고치고, 구간 ID·재생 가능 상태를 응답에 포함해 시간 탐색과 재생을 연결한다. 여러 카메라는 카메라별 조회로 시작할 수 있으며 일괄 API는 부하 근거가 있을 때 추가한다.
- 이전/다음 파일 자동 전환, 시간→파일 및 파일 내 offset 매핑, gap 정책과 연속 재생 버퍼링.
- 구간 썸네일 생성·캐시. 준비 전에는 시간 기반 간결한 행으로 표시 가능.
- 다중 카메라의 공통 시각 이동과 개별 로딩·누락 표시. 미세 드리프트 튜닝은 후순위다. 특정 카메라에 영상이 없다고 다른 카메라 시각을 임의로 바꾸지 않음.
- 관리자 구간 내보내기는 여러 파일 경계와 절단 처리를 지원해야 함. 현재 파일 다운로드와 명확히 구분.
- 모션/사람/차량 분류, 북마크는 확인된 현재 녹화 API 데이터가 아니므로 기본 설계에 포함하지 않음.

## 상태·반응형·검증 기준

- 녹화 없음/로딩/재생 실패/아직 마무리되지 않은 구간을 별도로 표시. 시간축의 공백 클릭은 녹화 없음을 보여주며 다음 녹화로 이동하는 명시적 동작 제공.
- 목록 선택 상태와 재생 시각, 카메라 라벨이 항상 일치. 전체화면 진입/복귀와 목록 열기/닫기에도 재생 유지.
- 키보드 Space, 좌우 이동과 탐색 컨트롤의 접근 가능한 이름·포커스 제공. 날짜/시간 입력 중 단축키가 입력을 가로채지 않음.
- 1920×1080뿐 아니라 1366×768, 실제 모니터링 PC 창 크기·DPI에서 검증. 공간이 작으면 보조 목록을 드로어로 전환하고 시간축을 압축. 모바일은 영상+조작부를 상단 유지하고 탐색 목록을 하단 시트로 제공.
- 영상과 필수 조작부는 첫 화면 안에 있어야 함. 목록 200/1000행에서도 영상 위치 불변. 사용자가 읽는 목록을 주기적 갱신이 강제 스크롤하지 않아야 함.
- 실제 파일 재생, 구간 경계, 공백, 자정 경계, 로딩 실패, 라이브 복귀를 각각 검증. 시간대는 KST로 일치시키되 내부 시간 값은 원래 계약 유지.
- 현재 산출물은 디자인 제안이다. 생성 이미지의 글자·눈금·픽셀은 실제 구현 검증을 대체하지 않는다.

## 타임라인 구현 타당성 재확인

사용자가 모든 목업의 타임라인이 현 녹화 구조에서 가능한지 지적하여 소스와 배포 API, 실제 MP4 탐색을 확인했다. 결론은 **완료된 녹화 파일의 구간 표시와 파일 내부 탐색 기반은 존재하지만, 재생 타임라인·연속 전환·정밀 동기화가 완성된 상태는 아니다.** AI 분석은 기본 녹화 시간축에 필요하지 않다.

### 직접 확인한 증거

- `routes_core.go`의 `/api/timeline`은 실제 DB의 ready/recording 구간을 반환한다. 배포 API에서 2026-09-09 한 카메라의 구간 44개, HTTP 200을 확인했다. `motion_events`는 0개이며 소스에서 빈 배열로 고정된다.
- 응답에는 시작·종료·상태가 있지만 구간 ID와 재생 URL은 없다. `cameraTypes.ts`의 TimelineData에는 응답의 status도 아직 선언되지 않는다.
- `LiveWorkspace.tsx`의 `TimelineBar.handleClick`은 blur만 실행한다. 클릭→시각→파일→재생 전환은 없다. 커서는 영상 재생 위치가 아니라 현재 시계이다.
- 같은 파일의 `TwoRowTimeline`은 선택 카메라 구간을 두 줄 모두에 전달한다. 전체 카메라 집계가 구현된 것으로 볼 수 없다.
- 운영 완료 녹화 ID 10861에 `Range: bytes=0-1023` 요청: HTTP 206, 1024바이트, Content-Range `bytes 0-1023/420732440` 확인.
- 별도 헤드리스 Chromium에서 같은 MP4의 metadata 로딩 후 currentTime=60 설정, seeked 이벤트와 readyState=4 확인. 실제 duration=1799.987125초, DB 구간 길이=1800초, 영상 2560×1440. 이는 샘플 한 개의 파일 내 탐색 가능 증거이며 전체 파일·코덱·공백 없는 전환·Windows 동기 재생의 검증을 뜻하지 않는다.

### 현재 녹화 인덱스의 중요한 한계

- `TimestampFromSegmentPath`는 `YYYY-MM-DD_HH-MM` 파일명에서 분 단위 시작 시각을 파싱한다.
- 정상 파일 교체 시 종료 시각은 다음 파일의 시작 시각, 프로세스 종료 시는 종료 처리 시각을 사용한다. 파일 내 실제 첫/끝 프레임의 절대시각을 저장하는 정밀 인덱스가 아니다.
- 따라서 예컨대 14:32:18 선택→14:30 파일의 138초 이동은 구현 가능하지만, 그것이 실제 벽시계의 14:32:18 장면이라고 확정할 근거는 부족하다. 재시작·첫 파일·키프레임 경계에서 오차가 생길 수 있다.
- 과거 파일은 미디어 duration/PTS 검증으로 범위 정확도를 개선할 수 있지만, 존재하지 않는 원래 절대시각 정보까지 완전히 복구한다고 약속하지 않는다. 신규 녹화에는 실제 미디어 타임스탬프와 기준 절대시각의 대응을 저장하는 설계·검증이 필요하다.
- 현재 play API는 ready만 허용한다. recording 구간을 현재 시각까지 막대로 칠할 수 있어도 그 부분은 재생 가능 구간이 아니다. 관찰된 운영 30분 세그먼트에서는 진행 중인 최신 파일의 완료 전 재생을 제공하지 않는다.
- 파일 한 개가 존재한다는 정보만으로 파일 내부 통신 단절이나 모든 프레임의 존재까지 증명할 수 없다. 기본 막대 의미는 '완료 녹화 파일이 있는 구간'으로 제한한다.

### 구현 순서와 통과 조건

1. 기존 API를 재생용 인덱스로 보완: ID, 상태, 범위 겹침, KST 경계. ready/recording/없음을 구분하고 실제 전체 카메라 합집합을 계산한다. 관리 콘솔 목록 제한을 재생 인덱스로 사용하지 않는다.
2. 단일 카메라 타임라인: 클릭 좌표→절대시각→구간 ID→파일 내 offset, metadata 이후 seek. 같은 파일 이동과 다른 파일 이동을 별도 처리하며 timeupdate는 재생 커서에 반영한다. API/컴포넌트를 Viewer와 콘솔에서 공통 사용하되 각 셸·권한은 유지한다.
3. 이전/다음 파일 전환 및 gap 정책: ended 이벤트와 다음 구간 로딩, 공백 알림/명시적 이동. 단일 video src 교체만으로 무중단 재생을 보장하지 않으며 필요 시 다음 파일 준비 방식 검증.
4. 썸네일은 별도 생성/캐시가 있어야 제공한다. 초기 버전은 시간 목록만으로 가능. 움직임/객체 이벤트 표시를 가짜로 채우지 않는다.
5. 라이브 화면의 다중 동기 재생은 이번 필수 범위이며 기반 구현 이후 연결한다: 먼저 절대시각-미디어 시각 대응을 검증하고 공통 시계·버퍼링·드리프트·누락 처리를 구현한다. 여러 video에 같은 currentTime을 주는 것만으로 정밀 동기화를 주장하지 않는다.

화면 구현 대상은 B 탐색형 녹화 화면과 기존 라이브 화면의 다중 동기 재생이다. 동기화 정확도는 실제 카메라로 검증해야 한다. 사용자 추가 요구에 따라 **진행 중 녹화의 최근 구간 재생은 필수 요구**로 포함한다. UI 변경만으로 완료하지 않고 아래 녹화·재생 기반 변경까지 필요하다.

## 진행 중 녹화 재생: 필수 요구와 기술 후보

사용자는 30분 파일 완료를 기다리는 최신 녹화 제한의 해결을 요구했다. 녹화가 계속되는 동안 수초 전 영상으로 돌아가 재생하고, 완료된 과거 녹화까지 같은 시간축에서 탐색할 수 있어야 한다. 로컬과 테스트 PC에서 실제 최대 2대 카메라로 파일 완료 전 재생되는지 확인한다. 부하 검사는 수행하지 않는다. 0초 지연을 의미하지 않는다.

공식 근거:

- [Frigate 녹화 프리셋 소스](https://github.com/blakeblackshear/frigate/blob/dev/frigate/ffmpeg_presets.py): 기본 녹화는 10초 MP4 세그먼트, 영상 copy 방식. 짧은 파일을 계속 완성하는 접근의 실제 사례다.
- [FFmpeg MP4 fragmentation](https://ffmpeg.org/ffmpeg-formats.html#Fragmentation): 영상과 관련 메타데이터를 fragment별로 기록하여 전체 파일 종료 전 읽을 기반 제공. faststart는 완료 시 인덱스 재배치이므로 진행 중 읽기 해결책이 아니다.
- [HLS 표준](https://datatracker.ietf.org/doc/html/rfc8216): fMP4 초기화, fragment 제공, byte range 및 갱신되는 재생 목록의 표준 기반.
- [AXIS 공식 설명서](https://help.axis.com/en-us/axis-camera-station-pro): 진행 중 녹화의 최근 5초 instant replay를 지원. 이것만으로 AXIS 내부 포맷이 fMP4라고 단정하지 않는다.

### CamStation에 우선 검증할 설계

30분 등 기존 보관 파일 단위 안에 키프레임 기반 짧은 fMP4 fragment를 기록하고, 완료 fragment의 시간·파일 offset·길이를 인덱싱한다. 새 조각을 공개하는 재생 API와 갱신되는 HLS 목록을 제공한다. 여러 조각을 각각 물리 파일로 만드는 대신 파일 내 byte range 또는 조각별 논리 URL로 제공할 수 있다. Viewer/웹은 HLS 재생 계층을 추가해 연속 수신한다. 기존 라이브 MSE 코드는 경험·일부 도우미를 재사용할 수 있지만 go2rtc WebSocket 전용 연결을 녹화 DVR로 그대로 재사용할 수는 없다.

데이터 흐름: 로컬 go2rtc → 녹화 worker → fMP4 보관 파일에 짧은 fragment 추가 → 완성된 fragment 인덱스 확정 → 재생 목록/조각 API → Viewer·웹 플레이어.

- parent 파일의 recording/ready 상태와 fragment의 재생 가능 상태를 분리한다. 기록 중인 파일도 완료 fragment까지만 재생 가능하다.
- 파일 증가 크기를 그대로 공개하지 않는다. 초기화 정보와 완전한 moof/mdat 경계, 시간 범위, 키프레임을 검사해 확정된 byte 범위만 제공한다. 정상 데이터 기록과 DB 게시의 일관성을 유지한다. 광범위한 crash 복구 고도화는 후순위다.
- 정상 파일 완료·temp→archive 이동 전후에도 같은 논리 ID로 기존 재생 요청이 이어져야 한다. 실제 파일 교체에 필요한 init 정보와 discontinuity를 처리한다. 다양한 코덱 변경·재시작 조합 검증은 추가하지 않는다.
- 백업은 완료된 보관 파일만, 삭제는 기존 미백업 보호와 재생 참조 보호를 적용한다. 진행 중 파일을 ready로 위장하거나 임시 디렉터리를 공개하지 않는다.
- fragment 인덱스는 필요한 범위만 저장·조회한다. 별도 쓰기·재구축 비용 벤치마크를 요구하지 않으며 운영 문제가 발생하면 대응한다.
- 코덱이 호환되면 영상 재인코딩 없이 remux 가능하다. 키프레임 간격이 길면 2초 설정만으로 2초 조각을 만들 수 없다. 카메라 GOP 조정 가능 여부를 먼저 확인하며 재인코딩 필요 여부를 따로 판단한다.
- 일반 MP4 다운로드 호환성이 필요하면 완료 파일 또는 선택 구간을 재인코딩 없이 재포장하는 경로를 검증한다. 기존 일반 MP4는 종전 재생 경로를 유지해 과거 자료를 보존한다.
- 우선 검증 목표는 GOP 1–2초 조건에서 수초 수준의 재생 가능 지연이다. 지연·복귀 시간은 로컬 환경과 테스트 PC에서 실제 최대 2대 카메라로 확인하며 현재 달성한 수치가 아니다. 기존 8대 실측 요구는 사용자 제약에 따라 제거한다.

### 로컬 타당성 실험

Ubuntu의 FFmpeg 6.1.1로 320×180, 25fps, GOP 50(2초)의 가상 영상을 16초 실시간 생성했다. 같은 인코딩 결과를 tee로 일반 MP4와 fragmented MP4에 동시에 기록했다. fMP4 옵션은 frag_keyframe+empty_moov+default_base_moof, flush_packets=1이었다.

- writer가 살아 있는 상태에서 일반 MP4: ffprobe 실패, moov atom not found.
- 같은 시점 fMP4: ffprobe 성공, 이미 기록된 duration 8초.
- 당시 fMP4 byte prefix를 고정해 2초 지점 프레임 디코딩 성공. 디코딩 후에도 writer 실행 중임을 확인.
- 정상 종료 후 양쪽 모두 duration 16초, writer exit=0.
- 실험 스크립트: `work/recordings-ux/active-recording-poc/probe.py`, 결과: `work/recordings-ux/active-recording-poc/result.json`.

이 실험은 파일 종료 전 읽기·디코딩의 기술적 가능성만 입증한다. 실제 카메라의 GOP/음성/코덱, HTTP 동시 읽기, HLS/MSE 연속 재생, 전원 장애, 파일 교체, 8카메라 부하는 아직 검증하지 않았다. 운영 녹화나 PC 설정은 변경하지 않았다.
