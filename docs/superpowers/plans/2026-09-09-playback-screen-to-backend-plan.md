# 라이브·녹화 공통 재생 구현·검증 범위

상태: 2026-09-09 사용자 최종 기준의 구현을 로컬에 반영하고 공통 기능을 검증했다. 테스트 PC를 운영과 동일한 MSI 2.0.29로 맞춰 Windows 화면 검증을 진행하고 있다. 운영 배포는 하지 않았다.

기준: [화면·이벤트 설계](../specs/2026-09-09-playback-screen-to-backend-analysis.md). 기존 집중 보기와 영상 더블클릭 줌 초기화는 그대로 유지한다. 이전 P1~P6 계획은 이 문서로 대체한다.

## 이번에 구현할 것

| 작업 | 구체 범위 | 관련 이벤트 |
| --- | --- | --- |
| B 녹화 화면 | 큰 단일 영상·우측 목록·하단 시간축. 웹은 기존 관리 기능을 별도 탭에 유지, 클라이언트는 재생 화면만 | E03/E10~12/E21~22/E24/E29/E32~34 |
| 라이브에서 녹화 탐색 | 기존 시간축에서 시각 선택→현재 배치의 모든 카메라가 같은 절대시각 재생. LIVE 클릭→실시간 복귀 | E01~06/E09/E15~18/E23 |
| 기존 집중 보기 연동 | 확대·복귀 시 모드·시각·pause·배속 유지. 새 확대 기능이나 제스처 개발 없음 | E07~08/E13~14 |
| 공통 재생 기능 | 날짜/시각 탐색, play/pause/±10초/배속/음량, 공백·오류·최근 구간 대기, 다음 녹화·재시도 | E02~06/E15~17/E21~23 |
| 녹화 기반 | 절대시각↔미디어 시각 매핑, 완성된 fMP4 조각부터 재생, 정상 파일 전환, 기존 MP4 호환 | B01~B05 |
| 기존 운영 보존 | 배치·줌·PTZ·녹화 관리 handler 재사용, 신규 녹화·기존 파일·미백업 삭제 보호 유지 | E19/E25~31/E35~36 |

화면 이벤트 대장은 누락 확인용이다. 기존 유지 이벤트를 새로 만들거나 이벤트 수만큼 테스트를 추가하지 않는다.

## 조건부로만 고칠 것

실제 코드 흐름이나 기능 확인에서 아래 문제가 이번 동작을 막는다고 확인될 때만 필요한 부분을 수정한다.

- 실제 보관 코덱이 대상 웹/클라이언트에서 재생되지 않으면 해당 코덱의 최소 재생 경로를 제공한다. 모든 코덱용 변환·캐시 시스템은 만들지 않는다(B06).
- 기존 연결/복구 동작이 녹화 재생을 강제로 종료하거나 라이브로 바꾸면 그 전환 조건만 고친다(E20). 연결 오류는 표시하되 새 관리 프로토콜·상태 보고 체계는 만들지 않는다(B07).
- 새 파일 식별/마감/기본 재시작 동작이 기존 녹화를 덮어쓰거나 재생을 막으면 해당 원인을 고친다. 별도의 포괄적 crash 복구 체계는 만들지 않는다.

운영 상태 표시만 더 세밀하게 만드는 작업, 정밀 동기 오차 튜닝, 숨겨진 타일 최적화, 성능·메모리 최적화, 드문 복구 조합, 장기 안정성 검증, 전체 버전 호환/롤백 행렬은 이번 범위에서 제외한다. 운영 중 구체적인 문제가 발생하면 그때 대응한다.

## 구현 순서·수정 위치

1. **화면 연결:** `ConsoleLayout.tsx`, `LiveWorkspace.tsx`, `RecordingsPage.tsx`에서 기존 셸·집중 보기·관리 기능을 보존하고 B 화면 및 이벤트를 연결한다. 공통 시간축·controls·녹화 hook만 필요한 만큼 추출한다.
2. **공통 상태:** `web/src/components/playback/`와 `web/src/app/`에 필요한 시각/재생 상태와 API 접근을 둔다. 같은 시계와 seek 세대를 사용해 늦은 응답이 최신 선택을 덮어쓰지 않게 한다. live hook은 기존 방식 유지. 독립 프레임워크나 사전 파일 분할은 하지 않는다.
3. **녹화·서버 연결:** `internal/recorder`, `internal/store`, recording/timeline route에서 완성 조각·시각 매핑·조회·미디어 전달을 구현한다. 필요한 데이터만 기존 구조에 추가하고 테이블 수를 미리 정하지 않는다. 시각 anchor 추출과 녹화 중 decode는 구현 과정의 작은 확인으로 해결하며 별도 실험 프로젝트를 만들지 않는다.
4. **네 화면 통합:** 같은 기반을 웹 라이브/녹화 및 테스트 PC 클라이언트 라이브/녹화에 연결한다. 클라이언트 전체화면은 기존 bridge 재사용. native/service 소스는 위 조건부 운영 차단 문제가 있는 부분만 수정한다.

완성 조각만 공개하고 정상 마감·다음 파일·과거 파일 재생을 이어야 한다. 실제 epoch 근거 없이 파일명 분 단위 시각을 정밀 시각으로 위장하지 않는다. 이 조건은 기능 정확성이지 성능 최적화 과제가 아니다.

## 기능 검증 — 로컬 + 테스트 PC, 실제 카메라 최대 2대

기존 허용 중계 입력을 공유해 카메라의 추가 송출을 최소화한다. 테스트가 카메라마다 웹·클라이언트·녹화·probe의 원본 세션을 따로 만들지 않게 한다. 사용자가 지정한 테스트 PC만 사용하고 기존 모니터링 PC를 임의로 시험 대상으로 삼지 않는다.

| 확인 묶음 | 확인할 동작 | 수행 범위 |
| --- | --- | --- |
| 녹화 화면 | 카메라/날짜/구간 선택, 영상 고정·목록 스크롤, play/pause/배속/음량, 관리 탭·목록 드로어 | 로컬 웹에서 공통 기능 확인, 테스트 PC는 셸/전체화면 차이 확인 |
| 라이브 연동 | 두 영상 같은 절대시각 이동, 기존 집중 보기 왕복에서 상태 유지, LIVE 복귀 | 로컬 웹 공통 동작 + 테스트 PC 동일 핵심 흐름 |
| 영상 연결 | 녹화 중 최근 조각 재생, 기존 MP4, 정상 다음 파일 전환, 공백의 다음 녹화·retry | 같은 기능 확인에 묶음; 경계는 필요한 작은 파일 fixture 사용 가능 |
| 수신 복구 | 테스트 측 수신을 닫았다 다시 연결, 재생 모드·위치 유지 | 실제 카메라 설정/연결은 건드리지 않고 수신 측에서 확인 |
| 운영 보존 | 새 녹화가 계속 저장되고 기존 파일/관리 기능을 해치지 않음 | 변경된 경계만 확인, 기존 관련 테스트 재사용 |

로컬·합성 소스에서도 부하/스트레스/성능 벤치마크는 하지 않는다. CPU/GPU/메모리/WAL 수치·지연 SLA·정밀 오차 목표를 출시 조건으로 두지 않는다. 프로세스 강제 종료·전원/DB crash 주입·장시간 반복도 하지 않는다. 카메라를 추가로 연결해 검사하지 않는다.

변경면에 맞는 프로젝트 필수 검사만 실행한다. UI 변경 시 web lint/build와 daemon build, 변경 로직의 기존 테스트를 사용한다. Go 변경 시 해당 테스트 및 통합 시 `go test ./...`, native 변경이 있을 때만 viewer-app test/build를 수행한다. 오류를 재현하는 작은 검사가 필요하면 그 검사만 추가한다. 통과한 검사를 화면·단계별로 반복하지 않는다.

## 종료 기준

요청 기능이 동작하고, 이번 변경으로 재생·녹화 등 실제 운영을 막는 구체적인 미해결 문제가 없으며 변경면의 필수 검사가 통과하면 종료한다. 기능 확인에서 실패하면 그 원인만 수정하고 영향받는 부분만 다시 확인한다. 성능 개선 가능성이나 가상의 드문 장애 때문에 완료를 미루지 않는다.

[설계 리뷰](../specs/2026-09-09-playback-design-review.md)는 위 범위와 이벤트 누락 여부를 확인한다. 구현·검증 완료를 뜻하지 않는다.

## 구현·검증 기록 — 2026-09-09

- B 화면, 공통 재생 엔진·시간축, 라이브 배치 전체의 절대시각 이동, 기존 집중 보기·LIVE 복귀, 녹화 viewport 공유를 구현했다. 관리 탭의 재생은 같은 B 플레이어를 사용하고 탭 왕복 시 pause·위치를 유지한다.
- PRFT 기반 fMP4 인덱스와 확정 조각 HLS API, 보관 카메라 카탈로그·시간 겹침 조회·안정 커서 목록을 구현했다. 정상 이동 뒤 논리 URL 유지, 삭제 410, 미완성 꼬리 제외, 기존 MP4 호환을 검사했다.
- 실제 중계 2개를 공유한 격리 로컬 녹화에서 파일 작성 중 Chromium 디코딩을 확인했다. 라이브 시간축 클릭의 두 카메라 동기 이동, 집중 보기 왕복, LIVE 복귀, B 날짜/카메라/관리 탭 전환, 공백의 다음 녹화, 정상 파일 전환, 수신 차단 후 재시도에서 상태 보존을 확인했다. 카메라 원본 설정은 변경하지 않았다.
- 전환 중 PTZ Stop의 늦은 응답이 최신 탐색을 덮는 문제와 Windows 관리 연결 복구가 녹화 경로를 종료하는 조건부 결함만 추가로 수정했다. 정상 파일 경계의 1초 이하 간격 처리는 파일 종료 후 이어받기에만 적용하며 명시적 빈 구간 탐색은 변경하지 않는다.
- Go 전체 검사, Web lint/build, daemon build, Viewer build가 통과했다. Web 전체 검사에서 기존 외부 플레이어 구조를 기대한 1개 검사가 실패해 동일한 Viewer 재생 전용 계약으로 갱신하고 해당 검사를 통과했다. Viewer는 최초 55개 중 54개 통과했다. 후속 감사에서 남은 소개 문구 정규식을 현재 스킬 탐색·대상·제어 계약 검사로 정합화했고, 전체 55개가 로컬과 Windows MSI 빌드에서 모두 통과했다.
- 초기 테스트 PC 버전 검증이 누락돼 MSI 2.0.24를 사용했다. 운영 NUC는 2.0.29였으며 EXE에 고정된 2.0.0은 설치 버전이 아니었다. 테스트 PC만 정확한 운영 2.0.29 MSI로 업데이트했고 설정·클라이언트 ID·서비스 환경 보존 및 EXE/앱 번들/서비스 해시 일치를 확인했다. 재실행 후 실제 Windows에서 서버 연결, 두 카메라 녹화 탐색·일시정지, 네이티브 전체화면 진입을 직접 확인했다. 사용자 클릭 요청은 철회했다. 실제 Windows에서 집중 보기 왕복의 일시정지 시각 유지, LIVE 복귀, B 화면 최초 자동 재생 없음도 확인했다.
- 브라우저의 Viewer 경로에서 라이브 최소 높이가 헤더 아래 가용 공간을 넘는 문제를 수정했다. 최종 빌드에서 시간축 하단이 창 안에 들어오는 것을 확인했다. 실기기 확인 대기 중에는 격리 테스트 녹화를 정상 종료하고 서버와 기존 테스트 파일을 보존했다.

- Viewer의 공통 헤더로 메뉴를 통합해 중복을 제거하고, 긴 녹화 시각 표시 때문에 라이브 격자가 창 밖으로 늘어나는 문제를 수정했다. 네이티브가 확인한 전체화면 상태를 화면 이동 뒤에도 공통 bridge가 복원한다.
- 최종 Windows B 화면에서 구간 선택 디코딩·일시정지, 라이브→녹화 이동 후 전체화면 상태 유지, 네이티브 전체화면 종료·재진입과 일시정지 시각 보존을 확인했다. 테스트 PC는 시각 검토를 위해 카메라 2대의 격리 서버에 연결된 녹화 화면으로 남겼으며 테스트 녹화는 꺼져 있다. 제어 작업·원격 실행 디렉터리 정리를 확인했다.
- 후속 감사의 네이티브 잔여는 테스트 MSI 2.0.30으로 마무리했다. 테스트 PC만 업데이트하고 설정·클라이언트 ID·서비스 환경과 설치 번들 해시를 확인했다. 관리 서비스를 정상 중지해 5초 뒤 시작한 실제 IPC 복구에서 같은 Viewer PID와 녹화 화면·18:51:04 KST 일시정지 위치를 유지했고 `management_recovered` 로그를 확인했다. 운영 배포는 하지 않았다. 최종 판정은 [완료 감사](../specs/2026-09-09-playback-completion-audit.md)를 참조한다.
