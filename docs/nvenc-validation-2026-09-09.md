# NVIDIA NVENC 구현·배포 검증

현재 상태: 운영 LXC 배포, GPU 출력 2개 전환 및 CPU 전후 비교 완료. 모든 시각은 별도 표시가 없으면 KST다.

## 구현과 재현 이미지

- 최종 운영 코드: `220a588aa658b03a73bea21ac25a6f111246708c`.
- 출력별 `videoEncoder=cpu|nvenc`, CPU 기본, 원본 복사 녹화 유지.
- 공유 출력당 인코딩 한 번. 복수 시청자가 인코더를 추가하지 않는다.
- 구성 배정과 실제 자식 프로세스 시작을 모두 최대 3세션으로 제한한다. 합성 검사도 실제 슬롯을 사용한다.
- GPU 고유 장애는 해당 출력만 CPU로 복구한다. 같은 go2rtc 실행 회차에서는 재연결 시 GPU 실패를 반복하지 않는다.
- FFmpeg 5.1.7, NVIDIA 470.256.02, nv-codec-headers 11.1.5.3, go2rtc 1.9.14, rclone 1.72.1을 고정했다.
- Forgejo 수동 빌드 run 39 성공. 이미지 config SHA-256은 `3ff52a5071661c8bb7303982983191efda8a47385affc7de597e5366952bc783`이다. 이 수동 빌드는 운영 배포를 실행하지 않았다.
- 최종 운영 빌드 run 41과 OpenShip 배포가 성공했다. 최종 이미지 config SHA-256은 `103056006fa12833851b4db6b9ed77381652054eea2c139e74308b1f52724126`, registry index digest는 `85b7f382765b4c41674e517c21ee68c6d40f8bf56f3f7cb8c371079a932f57b8`이다. 실제 운영 컨테이너의 revision·image ID·RepoDigest를 대조했다.

## 기능·복구 검사

- 전체 Go 검사, 변경된 supervisor/stream 실행 경계의 race 검사, 웹 모델 검사·lint·build 및 daemon build 통과.
- 실제 UID 10001에서 NVENC 인코딩, CPU 스케일/FPS/AAC, FLV 전달, MP4 segment copy와 ffprobe 검사 통과.
- 개발 실카메라 3대의 브라우저 재생을 확인했다. 4K NVENC·1080p CPU·360p copy가 정상 진행했고 브라우저 오류는 없었다.
- 4K 출력 수신자를 4명 추가해도 실제 NVENC PID 하나가 유지됐다. 수신자 4명 모두 정상 종료했다.
- 실제 NVENC 3개 동시 실행과 네 번째 요청의 CPU/`session_limit` 배정을 확인했다.
- 실행 중 GPU 장애 주입 후 CPU 재연결을 확인했다. go2rtc, 비대상 CPU 출력 및 녹화 3개의 PID는 유지됐고 활성 녹화 파일도 계속 증가했다.
- 복구 후 수신자 재연결 3회에서도 CPU를 유지했다. 이전 wrapper가 새 wrapper의 실행 상태를 덮는 경합을 발견해 수정하고 재검증했다.
- GPU 장치 없는 별도 컨테이너에서는 NVENC 요청이 `device_unavailable`로 CPU 전환되어 정상 H.264 파일을 생성했다.
- 기존 CPU 이미지로 같은 DB를 유지한 복귀 검사를 통과했다. 실제 GPU 인코더는 실행되지 않았고 영상·녹화가 정상 작동했다.

## 화질 비교

같은 3840×2160, 20fps 원본의 5초 구간을 비교했다. 점수는 원본 디코딩 영상 대비 값이며 Docker 실행 시간은 성능 비교에 사용하지 않았다.

| 설정 | 비트레이트 | SSIM | PSNR |
|---|---:|---:|---:|
| 기존 CPU | 18.620 Mbps | 0.979986 | 36.181 dB |
| NVENC 기본 비트레이트 | 2.228 Mbps | 0.893445 | 30.329 dB |
| 채택한 NVENC CQ23 | 20.954 Mbps | 0.980144 | 36.301 dB |

기본 NVENC에서는 수풀과 노면 질감 손실을 확인했다. `-rc vbr -cq 23 -b:v 0`를 적용한 결과는 이 표본에서 CPU와 유사했고 비트레이트는 약 12.5% 높았다. 모든 장면에서 동일한 품질·비트레이트를 보장한다는 뜻은 아니다.

## 장시간 관찰

개발 컨테이너의 8 CPU·4 GiB 조건에서 입력·해상도·FPS·수신 출력 수를 고정했다. CPU 5분 후 GPU 출력 1개를 28분 11초 관찰했다. 사용자가 관찰을 마치고 운영으로 전환하도록 요청하여 이 시점에 중단했다. GPU 출력 2개·3개의 추가 30분 관찰은 생략했으며, 앞선 3세션 실제 실행·공유 수신·장애 복구 검사는 수행했다. 전체 90분 관찰 통과로 보고하지 않는다.

CPU 평균은 6.379코어에서 4.108코어로 감소했다. GPU 단계의 세 수신 출력은 각각 20.007·14.999·20.001fps였으며, 측정 중 수신자 재연결·프레임 정지·GPU 복귀는 없었다. GPU 메모리는 206MiB, 온도는 52°C로 유지됐다. 원본 복사 녹화에서 실측한 입력 cadence를 기준으로 비교했으며, 카메라가 광고한 25fps와 실제 약 15fps의 차이를 기록했다. 인코더 자체 drop/dup 카운터와 이 GPU의 encoder utilization은 측정하지 못했다.

새 녹화 12개 모두 영상 스트림과 DB 크기 일치를 확인했다. 10개는 299초 이상, 나머지 2개는 약 296초였다. 해당 카메라에서는 약 304초와 296초 파일이 교대로 생성됐으며, 원본 복사·시계 기준 분할에서는 키프레임에 따라 미디어 길이가 달라질 수 있다. 검사기의 일률적인 299초 기준 미달과 사용자 요청 중단으로 남은 원시 결과 `pass=false`를 보존했으며 전체 장시간 검사 통과로 바꾸지 않았다.

초기 카메라 등록과 원본 연결 실패 중 생성된 빈 MP4 4개는 실패 산출물로 보존했으며 정상 녹화 검증에 포함하지 않았다. 초기 연결 대기로 실제 영상 길이가 짧아진 파일도 완전한 5분 세그먼트로 계산하지 않는다. 정상 안정화 이후의 새 세그먼트를 별도로 검사한다.

## 운영 LXC 및 CPU 비교

운영 LXC에 GPU 장치 4개를 매핑하고 한 번 재부팅했다. 호스트 드라이버는 유지하고 LXC에 격리된 470 사용자 공간 라이브러리와 NVIDIA 컨테이너 런타임을 구성했다. UID 10001의 실제 GPU 인코딩을 확인했으며, 기존 데이터 마운트와 포트 바인딩은 동일하다. DB quick check와 foreign key check도 정상이다.

전환 전 활성 녹화 8개를 모두 정상 종료하고 일관된 DB 백업을 남겼다. 10:59 KST에 첫 이미지 배포 후 8대 녹화를 재개했다. 설정 적용에서 이전 go2rtc 종료를 기다리지 않고 새 프로세스를 시작하는 포트 경합이 발생하여 CPU 설정으로 자동 복귀했다. 종료 완료 대기와 프로세스 상태 동기화를 수정하고 스트림·서버 race 검사 및 빌드를 통과했다. 로컬 반복 교체에서는 원본 충돌을 재현하지 못했으나 종료 완료 전 교체 금지 회귀를 검증했고, 수정 이미지의 운영 재적용 2회가 성공했다. 추가 LXC 재부팅은 하지 않았다.

11:10 KST에 소방서5 live, 11:11 KST에 소방서1 live를 GPU로 전환했다. 실제 NVENC 2개와 CPU 인코더 6개, 원본 복사 녹화 프로세스 8개를 확인했다. 각 공유 출력은 시청자 수와 무관하게 한 번 인코딩한다. 배포·적용 중 닫힌 녹화 16개의 영상과 DB 크기도 정상이다.

CPU는 배포 전 08:57:31–09:02:31, 배포 후 11:12:25–11:17:25에 각각 5초 간격 60개 표본으로 측정했다. 개발 인코딩·빌드 부하를 중지했으며, 배포 후에는 개발 컨테이너도 정지했다. 48논리 CPU인 Proxmox 전체의 사용 비율과 CamStation의 코어 환산 사용량을 구분한다.

| 지표 | 배포 전 | 배포 후 | 변화 |
|---|---:|---:|---:|
| Proxmox 전체 CPU, I/O wait 제외 | 16.03% | 9.68% | 6.34%p 감소, 상대 39.6% 감소 |
| CamStation CPU 코어 환산 | 5.34 | 2.43 | 54.5% 감소 |
| 호스트 I/O wait | 0.78% | 0.53% | 별도 관찰 |

최종 관찰 20회 모두 live 8/8, NVENC 2개·CPU 6개, 녹화 8개 정상 상태였다. 인코더 PID와 시청자 수는 유지됐으며, 각 활성 live 출력에 시청자 1명, focus 시청자는 없었다. 영상·녹화 출력 16개의 수신 바이트와 패킷, 활성 녹화 파일 8개의 크기가 모두 증가했다. LXC 외부에서 health HTTP 200도 확인했다. 전환 전후 정책을 대조했을 때 변경된 항목은 소방서1·5 live의 `videoEncoder`뿐이다.

배포 전 FFmpeg 8 CPU 이미지와 배포 후 FFmpeg 5.1.7 GPU 이미지를 비교하므로 배포 전체 효과이며, 순수한 인코더 변경만 분리한 실험은 아니다. 다른 호스트 작업의 영향을 없앤 측정도 아니며, 개발 LXC 자체의 평균 CPU는 0.316코어에서 0.087코어로 달라졌다. 추가 장시간 관찰, 인코더 자체 drop/dup 계수 및 운영의 완전한 30분 녹화 주기 관찰은 이번 완료 범위에 포함하지 않았다.
